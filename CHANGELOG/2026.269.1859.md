# 2026.269.1859 — fix(cua-hyprland-plugin): actually load the plugin + an in-repo box that proves it

## Summary of changes

Fixes a real producer defect the `check-cua-omarchy-vm` bed caught: the
`cua-hyprland-plugin` candy **built, installed, and referenced** the plugin from a file that
**nothing sourced**, so the plugin was never loaded.

The candy wrote `~/.config/hypr/cua-plugin.lua` (which calls
`hl.plugin.load("/usr/lib/cua/hyprland/cua-hyprland-plugin.so")`), but Omarchy 4.x's
`~/.config/hypr/hyprland.lua` loads a **FIXED `require()` list** (`default.hypr.*`, `hypr.*`)
and never referenced that file.

**Measured on the consumer guest** (before the fix):
```
$ cua-driver call type_text {"text":"x","delivery_mode":"foreground"}
{"ok":false,"code":"foreground_unavailable",
 "detail":"production Hyprland input plugin is unavailable","effect":"refused"}
$ HYPRLAND_INSTANCE_SIGNATURE=<sig> hyprctl plugin list
(empty — no plugins loaded)
```

The concrete edits (`candy/cua-hyprland-plugin/charly.yml`):
1. **The "load the plugin" run step now also appends `require("hypr.cua-plugin")`** to
   `~/.config/hypr/hyprland.lua` (idempotently, after Omarchy's own `require`s). Omarchy's
   `bootstrap.lua` puts `~/.config/?.lua` on `package.path`, so `require("hypr.cua-plugin")`
   resolves to the `~/.config/hypr/cua-plugin.lua` the candy writes.
2. **A new check `cua-hyprland-plugin-wired`** asserts the require is present in
   `hyprland.lua` whenever the plugin was built — the exact state the defect left absent.
3. **`base-devel` added** to the candy's packages — the in-repo build caught that cmake had no
   C++ compiler (`CMakeLists.txt:3 (project): No CMAKE_CXX_COMPILER could be found`).

Plus, in this repo:
4. **`cua-hyprland-plugin-test`** — an in-repo Arch box that composes the candy, plus
   **`cua-hyprland-fixture`** (a test-only candy seeding a minimal Omarchy-shaped
   `hyprland.lua` FIRST) so the candy's new append branch actually EXECUTES in-repo.
